# 知识库向量化（法规库 / 裁判案例库）设计

**日期：** 2026-09-04  
**状态：** 已定稿（P0 已实现）  
**范围：** 管理后台「知识库」双子页；上传 → 模型抽元数据 → 自动向量化入库；列表可改元数据。

---

## 1. 背景与目标

### 现状

- 管理后台「工具管理 → 向量化文档」为通用文本入库页，无法规/案例区分。
- `VectorService` 使用单一 Chroma 集合 `legal_documents`；metadata 支持 `title` / `source` / `category`，UI 未用类型过滤。
- 对话侧法规/类案检索仍大量依赖 MCP mock resource，与向量库未打通。
- 律所「案件管理」中的办案案件（民/刑/行/执）与裁判文书知识库是不同业务对象。

### 目标

1. 管理后台以 **知识库** 组织 **法规库**、**裁判案例库** 两个工作流入口（同一套向量基础设施，两套业务页）。
2. 用户 **上传文件** → **模型识别元数据** → **直接入库向量化**；入库后可在列表中编辑元数据。
3. 检索与统计按 `doc_type` 隔离，避免法规与案例互相污染。
4. 不把裁判案例挂在「案件管理」下，避免与办案案件混淆。

### 非目标（本设计不包含）

- 首版不强制改造对话编排立刻只走 Chroma（可后续把 `legal_retrieval` 接到过滤检索）。
- 不做人工「确认后才入库」门禁（产品已选自动入库）。
- 不引入第二套 embedding 模型或独立 MinIO 方案。
- 不做案由国家标准词表的完整治理（可先自由文本 + 后续规范化）。

---

## 2. 决策摘要

| 议题 | 决定 |
|------|------|
| 导航结构 | 知识库下两个子页：法规库 / 裁判案例库 |
| 向量存储 | **单集合 + `doc_type`**（`law` \| `case`），检索强制带类型过滤 |
| 入库交互 | 上传 → LLM 抽元数据 → **立即向量化**；列表可事后编辑 |
| 案例元数据 | 模型识别：案由、审判法院、审理程序、案号、审判人员、案例类型（普通/指导） |
| 法规元数据 | 模型识别：法律名称、效力级别、发布机关、文号、施行日期 |
| 与办案案件 | 隔离；裁判案例不属于 `cap.case_manage` 的案件 CRUD |

## 4. 端到端工作流

```
上传文件 → 解析正文 → LLM 按 schema 抽元数据
        → 写入知识条目（元数据 + 原文引用）
        → 切分并写入 Chroma（chunk metadata 带 doc_type + 业务字段）
        → 列表展示（可编辑元数据 / 删除 / 试检索）
```

### 4.1 上传与正文

- 支持格式：与现有文件服务一致（至少 `pdf` / `docx` / `txt`；与案件材料策略对齐时可再收窄）。
- 正文来源：优先 `FileService` 已有文本提取；失败则标记条目状态为 `extract_failed`，允许用户改元数据后重试向量化（首版可仅提示失败并允许删除重传）。

### 4.2 模型识别

- 使用项目已有 LLM 完成配置（`config.json` / admin LLM）。
- 输出 **严格 JSON**，按 `doc_type` 使用不同 schema；缺字段允许 `null`/空字符串，不阻断入库。
- 识别失败：仍入库原文向量（`doc_type` 必填），元数据置空，列表状态 `meta_partial` 或 `meta_failed`，便于事后补全。

### 4.3 自动入库

- 不弹确认框；上传任务成功即完成向量化。
- UI 展示进度：上传中 → 识别中 → 向量化中 → 完成/失败。
- 支持批量：首版可串行多文件（队列），避免打爆 LLM。

### 4.4 事后编辑

- 列表编辑元数据后：
  - **必须**更新持久化的知识条目元数据；
  - **必须**更新对应 chunk 的 Chroma metadata（或删旧向量再按新元数据重切——实现计划选定一种；推荐「更新 metadata，不改 chunk 文本」除非正文变更）。
- 正文变更（少见）：走「重新向量化」。

## 5. 数据模型

### 5.1 向量层（Chroma）

集合：继续使用 `legal_documents`（或配置项可改名，默认兼容现库）。

每个 chunk 的 metadata（示意）：

**公共**

| 字段 | 说明 |
|------|------|
| `document_id` | 知识条目 ID |
| `doc_type` | `law` \| `case` |
| `chunk_index` / `total_chunks` | 切分信息 |
| `title` | 展示标题（法规用法律名称；案例用案号或案由摘要） |
| `file_id` | 可选，关联 uploads |
| `source` | 可选，来源说明 |

**法规 `doc_type=law`**

| 字段 | 中文 |
|------|------|
| `law_name` | 法律名称 |
| `effect_level` | 效力级别 |
| `issuing_authority` | 发布机关 |
| `document_number` | 文号 |
| `effective_date` | 施行日期 |

**案例 `doc_type=case`**

| 字段 | 中文 |
|------|------|
| `cause_of_action` | 案由 |
| `court` | 审判法院 |
| `procedure` | 审理程序（一审/二审/再审等，模型自由或枚举） |
| `case_no` | 案号 |
| `judges` | 审判人员 |
| `case_kind` | 案例类型：`ordinary` 普通案例 / `guiding` 指导案例 |

检索 API：**所有** 面向法规或案例的查询必须带 `where`（或等价过滤）限制 `doc_type`。

### 5.2 应用层条目（建议）

为支持列表编辑与状态，不宜只靠 Chroma。建议 SQLite（可新表或扩展现有库，与 `files.db` / `rbac.db` 分离亦可）：

`kb_documents`（示意）：

- `id`（= `document_id`）
- `doc_type`
- `file_id`
- `title`
- `status`：`processing` \| `ready` \| `meta_failed` \| `vector_failed` \| `deleted`
- `meta_json`（完整业务元数据）
- `created_at` / `updated_at` / `created_by`

删除：软删或硬删；硬删须同步删 Chroma 中该 `document_id` 全部 chunk。

## 6. API 与服务（逻辑边界）

在 MCP/HTTP 上扩展（命名可在实现计划中细化）：

| 能力 | 说明 |
|------|------|
| 上传并入库 | `doc_type` + `file_id`（或 multipart）→ 抽文本 → LLM → 写条目 → 向量化 |
| 列表 | 按 `doc_type` 分页；返回元数据与状态 |
| 更新元数据 | 更新 `meta_json` + 同步向量 metadata |
| 删除 | 条目 + 向量 |
| 试检索 | `doc_type` + query + 可选过滤字段 |
| （可选）仅重抽元数据 / 仅重向量化 | 失败重试 |

LLM 抽取：独立可测的 prompt + JSON schema 校验模块（法规/案例各一份）。

切分策略：

- 法规：可略偏「按条/自然段」，长度与现网 chunk（约 500/50）可配置。
- 案例：按段落切分即可；首版可与法规共用切分参数，后续再分化。

## 7. 管理后台 UI

### 7.1 法规库页

- 主操作：上传法规文件（可多选串行）。
- 列表列：法律名称、效力级别、发布机关、文号、施行日期、状态、操作（编辑元数据 / 删除 / 查看原文）。
- 侧栏或浮层：编辑元数据表单；试检索（限定 `doc_type=law`）。

### 7.2 裁判案例库页

- 主操作：上传裁判文书。
- 列表列：案号、案由、法院、审理程序、案例类型、审判人员、状态、操作。
- 编辑浮层：可改正文识别结果；案例类型用枚举（普通/指导）。
- 试检索：限定 `doc_type=case`，可选按案由/法院/程序/类型过滤（首版至少支持关键词 + 类型）。

### 7.3 交互原则

- 上传后立即给出任务反馈，不阻塞整个页面（若同步实现，至少禁用重复提交并显示进度文案）。
- 元数据为空时列表显示「—」，不假装识别成功。

| 模块 | 关系 |
|------|------|
| `vector_service.py` | 扩展 add/search/list/count，支持 metadata 过滤与批量更新 metadata |

| Orchestrator `legal_retrieval` | 本设计不强制改造；后续可将 mock 换为按 `doc_type` 的向量检索 |

## 9. 风险与约束

1. **自动入库错误元数据** 会影响过滤质量 → 依赖列表可编辑与「meta_failed」可见性。  
2. **PDF 扫描件** 无文本 → 需明确失败状态；OCR 不在首版范围。  
3. **旧 `legal_documents` 无 `doc_type`** → 迁移策略：视为未知，不参与法规/案例页列表；或一次性脚本打标。  
4. **LLM 费用与耗时** → 串行队列 + 超时与失败重试。  
5. Chroma metadata 值类型限制（通常为标量）→ 审判人员等多值可存为分隔字符串。

---

## 10. 验收标准

1. 导航可见「法规库」「裁判案例库」两个入口，权限受 `cap.vectorize`（及页面权限）控制。  
2. 上传法规文件后自动出现在法规库列表，且向量检索（限定 law）能命中。  
3. 上传裁判文书后自动出现在案例库列表，元数据字段由模型填充（允许部分为空）；检索限定 case。  
4. 编辑案例/法规元数据后，再次按过滤条件检索行为与新元数据一致。  
5. 法规检索结果中不出现 `doc_type=case` 文档，反之亦然。  
6. 删除条目后原文件向量不可再被检索到。
